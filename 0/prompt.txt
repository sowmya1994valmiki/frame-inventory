Checkpoint 3 — Frame History Behaviour

Use the existing history persistence model already implemented in this project from Checkpoint 1.

Stick to the current design:
- one frame_history table
- FrameHistory references Frame by frame_id
- HistoryEventType: CREATED, IMPORTED, UPDATED
- HistorySource: MANUAL, CSV_UPLOAD
- occurredAt timestamp
- changedFields stored as JSON with old/new values
- append-style history
- no generic audit framework
- no event sourcing

Implement only:

1. Manual create
- create a CREATED history record
- source = MANUAL
- changedFields = {}
- UTC timestamp

2. Manual update
- create an UPDATED history record only when business fields actually changed
- capture only changed fields
- use old/new values
- use nested paths such as location.postcode, site.siteNumber, technical.pixelWidth
- source = MANUAL
- do not treat modifiedDate alone as a business change

3. No-op update
- do not create an UPDATED history record if no business value changed
- preserve existing PUT behaviour

4. History API
Add:
GET /api/frames/{frameId}/history

- keep it in the existing FrameController
- return newest-first
- use FrameHistoryResponse DTO
- return existing 404 behaviour for missing frame

5. Tests
Cover:
- CREATED history
- UPDATED history
- changed fields only
- nested field change
- multiple fields changed in one update
- no-op update
- newest-first retrieval
- missing frame

Keep the frame update and history insert in the same transaction.

Keep the implementation simple and appropriate for this take-home exercise:

- keep the history logic close to the existing FrameService unless a separate service is clearly justified
- avoid reflection-based or generic diff frameworks
- avoid unnecessary abstractions, interfaces, factories, strategies or additional layers
- do not introduce new dependencies unless genuinely required
