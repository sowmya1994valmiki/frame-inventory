CHECKPOINT 1 — DESIGN DECISIONS

The overall approach looks good. Before implementation, I want to confirm a few decisions.

1. Frame ID

Keep frame_id required and unique. Once created, it should not be editable. Keep it read-only in the edit UI and don't allow the update API to change it.

Also check whether frame_id itself can be the database primary key. Use a separate generated ID only if there is a clear benefit.

2. CSV duplicates

I prefer create-only import unless the requirements say otherwise. New frame IDs should be created; existing frame IDs should be reported as duplicates rather than updated.

3. CSV failures

I prefer row-level processing where possible. Valid rows can be imported and failed rows should be reported with the row number and reason.

If atomic whole-file import is more appropriate based on the requirements, explain why.

4. Frame history

Keep one frame_history table rather than separate history_events and history_changes tables.

Each history record should contain the frame reference, event type, timestamp/source and changed fields as JSON with old and new values.

For updates, store only the fields that actually changed.

For example:

{
  "status": {
    "old": "INACTIVE",
    "new": "LIVE"
  }
}

For CREATED or IMPORTED events, the history record can contain minimal or empty change details.

Keep this simple and avoid a generic audit/event-sourcing framework.

5. Java model grouping

The CSV has around 45 columns, so I don't want one large flat Frame class.

Group related fields using @Embeddable / @Embedded where it improves readability, while keeping all those columns in the same frames table.

Consider groups such as:
- location
- technical/display
- commercial/pricing
- external integration details

Keep important/common fields directly on Frame.

The purpose is Java code readability, not database normalization. Don't create extra tables just for these groups.

Show me the proposed Frame fields and embedded groups before implementation.

6. Search

Use MariaDB/JPA for search. Don't introduce OpenSearch unless there is a clear requirement that justifies the additional complexity.

7. General approach

Keep the solution simple and focused on the exercise. Avoid unnecessary libraries, infrastructure, abstractions and design patterns.

Please respond with:
- the revised decisions
- proposed Frame and @Embeddable structure
- final CSV behaviour
- final history structure
- any remaining decisions that genuinely need my input
